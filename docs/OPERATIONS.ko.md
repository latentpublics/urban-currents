## 1. 자리를 비웠다 돌아왔을 때 — 이것만 하십시오

```bash
cd C:\Users\jour\Documents\GitHub\urban-currents
uv run uc status
```

`uc status`는 **"무슨 일이 있었나"보다 "뭔가 잘못됐나"에 먼저** 답합니다.

| 필드 | 뜻 | 이게 이상하면 |
|---|---|---|
| `last_success` | 마지막으로 정상 종료한 실행 | 며칠 전이면 스케줄이 멈춘 것 |
| `last_issue` | 마지막으로 발행된 이슈 날짜 | `last_success`와 함께 봐야 뜻이 생깁니다 |
| `unpublished_dates` | **못 본 날들** | 비어 있지 않으면 `uc catch-up` |
| `silent_sources_last_run` | OK로 끝났는데 **아무것도 안 가져온 소스** | 아래 §6의 "성공을 보고하는 실패" |
| `consecutive_failures` | 연속 실패 일수 | 2 이상이면 소스나 키 문제 |
| `llm_cost_total_usd` | 누적 LLM 지출 | 예산 감각용 |
| `lock` | 다른 실행이 잡고 있는 잠금 | 오래 남아 있으면 §6 |

> **`last_success`가 `null`인데 이슈가 여러 개인 것은 정상입니다.**
> 실행 로그(outcome model)가 생기기 전에 발행된 이슈들이라 로그 행이 없습니다.
> `last_issue`가 나머지 절반의 답입니다.

`uc status`는 **못 본 날이 있으면 0이 아닌 종료 코드**를 냅니다. 그래서 점검용으로도 씁니다.

### 못 본 날이 있으면

```bash
uv run uc catch-up     # 지평선 안쪽의 놓친 날짜를 오래된 것부터 재시도
uv run uc weekly       # 지난 7일의 결과 · 지출 · 발송 요약
```

**`catch-up`은 하루가 실패해도 나머지를 멈추지 않습니다.** 며칠 자리를 비워도
돌아와서 이 한 줄이면 따라잡습니다.

### 보류된 것이 있으면 (Phase 0L에서 새로 생겼습니다)

```bash
uv run uc review --pending
```

**이것이 매일 검수를 대체하는 명령입니다.** 날짜를 묻지 않습니다 —
일주일을 비우면 일주일치가 쌓여 있고, **그 날짜들을 기억하는 것이 바로 없애려는
마찰**이기 때문입니다.

- 한 번에 **25건**만 보여주고 남은 수를 알려줍니다. 중간에 `quit`으로 끊어도 됩니다.
- **보류(withheld)가 근접(near miss)보다 먼저** 나옵니다.
  보류는 이슈에서 한 자리를 뺏은 것이고, 근접은 아무 대가도 없었습니다.
- 판정 결과는 라벨이 되고, 그 라벨이 규칙을 고칩니다.

## 1-2. 검수가 무엇으로 바뀌었는가 ★

| | 이전 | **지금** |
|---|---|---|
| 언제 | 매일 | **돌아왔을 때** |
| 무엇을 | 발행 **전** 전수 | 발행 **후** 표본 + 보류분 |
| 막는 것 | 사람이 매일 | **선정 정책이** (보류 큐) |

| 명령 | 쓰임 |
|---|---|
| `uc review --pending` | 보류 큐. **돌아왔을 때 치는 명령** |
| `uc review --sample --since 2026-08-11` | 이미 나간 것의 층화 표본 읽기 |
| `uc review --date 2026-08-11` | 특정 날의 전체 검수 |
| `uc review --relabel weak` | `drop_weak` 15건을 방법/결과로 쪼개기 (5분) |

> **`--latest`는 일부러 만들지 않았습니다.** 인자 없이 "오늘 것 보여줘"가 되면
> **매일 아침 확인하라는 신호**가 되고, 그것이 이 설계가 없애려는 습관입니다.

### 보류 큐란 무엇인가

확신이 없는 항목은 **싣지 않고 보류**합니다. 그날 이슈는 **그 자리를 비운 채**
나갑니다. **구멍이 정답입니다** — 자신 없는 것으로 채운 자리는 독자에게
채워진 것으로 보이고, 독자는 둘을 구별할 수 없습니다.

**보류분은 다음 이슈로 넘기지 않습니다.** 독자에게 빚진 것이 아니라
**판정을 기다리는 것**입니다.

```bash
uv run python scripts/held_rate.py    # 규칙이 얼마나 잡는지
```

> **보류율이 30%를 넘으면 규칙이 너무 넓은 것입니다** — 그 지점부터는 필터가 아니라
> 사고로 채택된 다른 편집 방침입니다.
> **2026-08-18 실측: 0.2917 (모집단 1일).** 그리고 숫자보다 나쁜 것이 있습니다 —
> **보류된 7건 중 4건이 명백히 도시 논문**입니다(도시열섬 · 스마트시티 데이터 거버넌스 ·
> 해안도시 홍수 회복력). 환경과학 서브필드를 달고 들어와서 걸렸습니다.
> **박사님이 가장 먼저 볼 것이 이것입니다.**

## 2. 매일 도는 실행

```bash
uv run uc daily              # 창을 수집 → 판정 → 발행 → 발송
uv run uc daily --dry-run    # 전부 돌리되 아무것도 쓰지 않고 보내지 않음
```

### 창(window)이 7일인 이유

이슈 날짜는 **논문이 나온 날이 아니라 우리가 처음 본 날**입니다. 두 소스의 색인이
늦기 때문입니다.

| 소스 | 색인 지연 | 근거 |
|---|---|---|
| 저널 (OpenAlex) | p50 **1일** · p90 **2일** · p99 17일 | 저장된 응답 4,674건 |
| **arXiv** | **3일** | 2026-08-18에 물으니 직전 3일이 전부 0건, D-4부터 하루 221~453건 (주말 포함) |

`uc daily`는 `[오늘-7, 오늘-1]`을 봅니다. **느린 쪽(arXiv 3일)에 맞춰 넓힌 폭**입니다.
이미 발행된 항목은 건너뛰므로 창이 겹쳐도 두 번 실리지 않습니다.

> **처음 이 창을 3일로 잡았다가 arXiv 사각지대에 통째로 들어앉은 적이 있습니다.**
> 그때 모든 스테이지가 `OK`였고 arXiv만 0건이었습니다. 그 사고가
> `silent_sources` 경보를 만들었습니다.

### `--dry-run`도 돈이 듭니다

요약 스테이지까지 진짜로 돌리고 쓰지만 않습니다. **약 $0.14, 7분** (7일 창 기준).
비싼 스테이지를 건너뛰는 예행연습은 **가장 잘 깨지는 것을 시험하지 않는 것**이라
일부러 그렇게 만들었습니다.

`--dry-run`은 `content/runs_log/`에 **행을 남기지 않습니다.** 예행연습은 그날을
"본 것"이 아닙니다.

### 종료 코드

| 코드 | 뜻 |
|---|---|
| `0` | 정상 (발행 또는 조용한 날) |
| `1` | **못 본 날** (`not_published`) |
| `75` | 다른 실행이 잠금을 쥐고 있음 |

## 3. ★ 하루의 결과는 셋입니다 — 이 구분이 이 서비스의 전부입니다

| 결과 | 뜻 | 이슈 파일 | 이메일 |
|---|---|---|---|
| `published` | **봤고**, 실을 것이 있었다 | 쓴다 | 보낸다 |
| `quiet` | **봤고**, 실을 것이 거의 없었다 | 쓴다 | 보낸다 |
| `not_published` | **못 봤다** | **안 쓴다** | **안 보낸다.** 대신 경보 |

**실패한 날은 조용한 날이 아닙니다.** `quiet`을 주장하려면 넷을 다 만족해야 합니다:

1. 필수 소스가 전부 **OK로 종료**했고
2. **후보 모집단을 실제로 셌고** (0을 센 것과 세지 못한 것은 다릅니다)
3. FAILED인 스테이지가 없고
4. 예산이 온전할 것

하나라도 아니면 이슈를 쓰지 않고 `content/runs_log/YYYY-MM-DD.json`에 이유를 남깁니다.

## 4. ★★ 스케줄 켜는 절차 6단계 — 무엇이고 왜 이 순서인가

**이건 매일 하는 일이 아닙니다. 처음 한 번, 순서대로 하는 일입니다.**

`.github/workflows/daily.yml`과 `weekly.yml`은 이미 커밋돼 있고,
**`schedule:` 블록이 주석 처리**돼 있어 스스로 돌지 않습니다.
지금은 GitHub 웹에서 손으로만 실행할 수 있습니다(`workflow_dispatch`).

순서의 원칙: **낯선 사람에게 무언가 도달하기 전에, 사람이 그 내용을 먼저 읽는다.**

### ★ 0단계 — 저장소 Secrets 등록 (원래 문서에 빠져 있었습니다)

**1단계보다 먼저 해야 합니다.** 키가 없으면 2단계가 반드시 실패합니다.

GitHub 웹에서:

> **저장소 → Settings → Secrets and variables → Actions → `New repository secret`**
> (주소로 바로: `https://github.com/youngjour/urban-currents/settings/secrets/actions`)

| Secret 이름 | 값 | 없으면 |
|---|---|---|
| `OPENALEX_KEY` | 로컬 `.env`의 같은 값 | **저널 수집 실패 → 이슈 발행 안 됨** |
| `GOOGLE_API_KEY` | 로컬 `.env`의 같은 값 | 요약 없이 카드만 발행 |
| `CONTACT_EMAIL` | 연락용 이메일 | OpenAlex 요청 헤더에만 쓰임 |
| `SPRINGER_API_KEY` | (선택) | Springer 초록 12건 손실 |

`.env` 값을 그대로 복사하면 됩니다. **한 번 등록하면 값은 다시 볼 수 없습니다**
(GitHub이 가려 버립니다). 바꾸려면 지우고 다시 만듭니다.

`UC_ALERT_RECIPIENT`은 **3단계**에서, `UC_SMTP_*`는 **6단계**에서 넣습니다.


| 단계 | 무엇을 하나 | 끝나면 어떤 상태 | 누구에게 도달하나 |
|---|---|---|---|
| **0** | **Settings → Secrets → Actions에 `OPENALEX_KEY` · `GOOGLE_API_KEY` 등록** | 러너가 API를 부를 수 있음 | **아무도** |
| **1** | Actions → daily → Run workflow, `dry_run: true` **+ `smoke: true`** | 설치·모델 캐시·API 키 확인. **3~6분** (첫 실행은 모델 440MB 때문에 더 걸립니다) | **아무도** |
| **2** | 같은 화면에서 `dry_run: false` | 이슈가 쓰이고 커밋됨. 메일은 러너 안 `.eml`로 만들어졌다 사라짐 | **아무도** |
| **3** | 저장소 Secrets에 `UC_ALERT_RECIPIENT` 등록 | 실패 경보가 살아남 | **박사님 한 명** (운영 메일) |
| **4** | `daily.yml`의 `schedule:` 주석 해제 | **스스로 매일 돌면서 아카이브에만 발행.** 메일은 아무에게도 안 감 | **아무도** |
| **5** | `weekly.yml`의 `schedule:` 주석 해제 | 주 1회 운영 요약 메일 | **박사님 한 명** |
| **6** | 제공자 선택 → 도메인 → SPF/DKIM/DMARC → `UC_SMTP_*` → `deliver.backend: smtp` | 독자에게 발송 시작 | **묻지 않은 사람들** |

> **`smoke: true`를 켜십시오.** 창을 2일로 좁히고 요약을 3건만 합니다.
> 켜지 않으면 1단계가 **7일 창 전체를 수집하고 전부 요약**합니다 —
> 파이프라인에서 가장 비싼 일을 시켜 놓고 결과를 버리는 것이고,
> **첫 시도에서 45분에 잘린 것이 바로 그 실행입니다.**

### 각 단계를 GitHub 어디에서 하는가

| 단계 | 어디 |
|---|---|
| 0 · 3 · 6(키) | **Settings → Secrets and variables → Actions** |
| 1 · 2 | **Actions → 왼쪽 `daily` → 오른쪽 `Run workflow` 버튼** |
| 4 · 5 | **저장소의 `.github/workflows/daily.yml` 파일 → 연필 아이콘 → `schedule:` 두 줄의 `#` 삭제 → Commit** |
| 6(설정) | `config/pipeline.yaml`의 `deliver.backend` |

`Run workflow` 버튼을 누르면 작은 창이 뜨고 `date`(비워 두면 오늘)와
`dry_run`(기본 `true`) 두 칸이 있습니다. **2단계는 `dry_run`을 `false`로 바꿔서**
실행합니다.


### 4단계가 정확히 무엇인가

**`daily.yml` 파일 안의 주석 두 줄을 지우는 것**입니다. 그러면 GitHub이 매일 아침
`uc daily`를 대신 돌려 줍니다. 그 결과는:

- 이슈가 만들어져 저장소에 커밋됩니다
- 사이트(`site/`)가 다시 빌드됩니다
- **이메일은 `file` 백엔드라 러너 안에서 `.eml` 파일로 만들어졌다 사라집니다**
- **따라서 이 단계에서는 아무에게도 메일이 가지 않습니다**

제가 지시서에 *"일주일 두고 매일 아침 아카이브를 낯선 사람처럼 읽으십시오"*라고 쓴 것은
**그 일주일 동안만의 길들이기(burn-in)**입니다. 매일 15분씩 검수하라는 뜻이 아니라,
**켜자마자 6단계로 달려가지 말고 일주일쯤 눈으로 훑어보라**는 뜻이었습니다.
그리고 그마저도 **하루 이틀 건너뛰어도 아무 일도 일어나지 않습니다** —
아카이브는 남아 있고 `uc status`가 나중에 다 알려줍니다.

### 3단계와 5단계의 메일은 다릅니다

- **3단계 경보 메일**: 뭔가 잘못됐을 때만. 제목에 날짜와 이유가 있어서 **열지 않고
  판단**할 수 있습니다. 연속 실패는 문구가 달라집니다.
- **5단계 주간 요약**: 주 1통. 지난 7일의 결과·지출·발송.
- **둘 다 발송 원장(`content/deliveries/`)에 남지 않습니다.** 남으면 그날이
  독자에게 나간 것처럼 보이기 때문입니다.

### 켜기 전에 알아 둘 것 둘

- **GitHub은 저장소가 60일간 조용하면 예약 워크플로를 자동으로 끕니다.**
  봇 자신의 커밋이 그 시계를 되돌리는지는 공식 문서로 확인하지 못했습니다.
  **주간 요약이 안 오는 것**을 그 증상으로 의심하십시오.
- **예약 실행은 최선 노력이라 부하가 걸리면 늦게 돕니다.** 여기서는 문제가 안 됩니다 —
  창이 7일이고 `catch-up`이 일주일을 따라잡습니다.

## 5. 필요한 키 — `.env`

**`.env`는 절대 커밋하지 마십시오.** 이미 `.gitignore` 최상단에 있습니다.

| 변수 | 무엇 | 없으면 |
|---|---|---|
| `OPENALEX_KEY` | OpenAlex API 키 (무료 $1/일) | 저널 경로가 `SKIPPED`, arXiv만 돎 |
| `GOOGLE_API_KEY` | Gemini (기본 요약 제공자) | 요약 없이 카드만 발행 |
| `UC_PREVIEW_RECIPIENT` | 미리보기 수신자 (지금은 박사님) | 발송 없음 |
| `UC_ALERT_RECIPIENT` | 실패 경보 수신자 | 경보 없음 |
| `UC_SMTP_*` | 발송 자격 증명 (6단계에서) | `file` 백엔드로 자동 강등 |
| `SPRINGER_API_KEY` | (선택) Springer 초록 회수 | 저널 경로 초록 12건 손실 |

> **[고침 — Phase 0L, M3-2]** 영문 원본의 실패 표에 `ANTHROPIC_API_KEY`라고
> 적혀 있던 것을 **`GOOGLE_API_KEY`로 고쳤습니다.** 기본 제공자가 Gemini이기
> 때문입니다 (`config/pipeline.yaml`의 `llm.provider: gemini`).
> 자리를 비운 사람이 **있지도 않은 키를 찾게 만드는** 종류의 오기였습니다.
> 제공자를 Anthropic으로 바꾸면 그때는 `ANTHROPIC_API_KEY`가 맞습니다.

## 6. 문제가 생겼을 때

| 증상 | 뜻 | 조치 |
|---|---|---|
| `uc daily`가 **75**로 종료 | 다른 실행이 잠금을 쥠 | 기다리십시오. 주인이 죽은 잠금은 자동 회수되고, 살아 있는 프로세스가 쥔 것은 **일부러** 거부합니다 |
| `status: not_published` | **그날을 못 봤다** | `content/runs_log/`의 `reasons`가 넷 중 무엇이 실패했는지 말합니다. `uc catch-up` |
| `silent_sources: ["collect.arxiv"]` | 소스가 **OK로 끝났는데** 창 전체에서 0건 | **성공을 보고하는 실패입니다.** `daily.lookback_days`를 소스의 색인 지연과 대조하고, 그다음 소스 자체를 보십시오. 발행을 막지 않으므로 **이것 말고는 알려 줄 것이 없습니다** |
| `collect.openalex: SKIPPED` | `OPENALEX_KEY` 없음 | arXiv 쪽은 돕니다. 키를 넣고 `uc collect` 재실행 |
| `summarize: SKIPPED` | `GOOGLE_API_KEY` 없음 | 요약 없이 발행됩니다. 키 넣고 `uc summarize` 재실행 |
| `summarize: PARTIAL` | 호출 상한에 걸림 | `llm.max_summaries_per_run`을 올리거나 내일 재실행 |
| `BudgetExceeded` | OpenAlex 일일 예산 80% | 그날은 멈춥니다. **UTC 자정에 초기화** |
| "Summary pending review." 카드 | LLM 출력이 스키마를 두 번 위반 | 검수에서 손보거나 프롬프트 수정 후 재실행 |
| 경보 로그에 `alert_failed` | 메일이 못 나감 | **실행 로그는 여전히 정확합니다.** 경보는 로그의 사본이지 기록이 아닙니다 |
| **Actions 잡이 빨간 X, 마지막 단계가 `Fail the job if the day was not published`** | **이건 크래시가 아니라 판정입니다.** 그날을 못 봤다는 뜻이고, 잡을 일부러 빨갛게 만듭니다 | 아래 §6-1 |
| `collect.openalex finished FAILED` (러너에서) | **Secrets에 `OPENALEX_KEY`가 없습니다** (§4의 0단계) | 등록 후 2단계 재실행 |
| `stages failed: classify` (러너에서) | **학습된 분류기 파일이 저장소에 없습니다** — `models/*.joblib`가 `.gitignore`에 걸려 있습니다 | 아래 §6-1. 코딩에이전트가 고칩니다 |
| 봇이 푸시 못 함 | 그 사이 누가 푸시함 | 자동으로 rebase 후 **1회** 재시도. 두 번째 실패는 멈추고 경보 — 사람이 봐야 합니다 |

**절대 하지 말 것: `git push --force`.** 봇의 푸시를 성공시키려고 남의 커밋을 버리는 것은
**다시 돌려서 되돌릴 수 없는 유일한 고장**입니다.

### 6-1. 2026-08-18에 실제로 있었던 2단계 실패 (알려진 결함 둘)

박사님이 2단계를 돌렸을 때 나온 것입니다. **설정 실수가 아니라 시스템 쪽 결함 둘입니다.**

원격 커밋 `d4648f2`의 실행 로그:

```json
"failed_stages": ["classify", "collect.openalex"],
"reasons": ["collect.openalex finished FAILED", "stages failed: classify, collect.openalex"],
"candidates": 0, "spend_usd": 0.0, "status": "not_published"
```

**같은 날짜를 로컬에서 돌렸을 때는 후보 208건 · 발행 21건 · $0.145로 정상**이었습니다.
파이프라인은 멀쩡하고 **러너 환경에 두 가지가 없습니다.**

| # | 원인 | 상태 |
|---|---|---|
| 1 | **Secrets에 `OPENALEX_KEY`가 없음** | **박사님이 §4의 0단계로 해결하십시오** |
| 2 | **`models/clf-v2-2026-08-13.joblib`(3.9KB)이 `.gitignore`에 걸려 저장소에 없음** | **고쳤습니다** (H1, 커밋 `2630954`) |

**H1은 고쳐졌습니다.** `models/*.joblib` 다섯 개를 커밋했습니다(전부 합쳐 20KB).
`git archive HEAD`로 뽑은 깨끗한 트리에서 핀이 걸린 모델이 **로드되는 것까지**
확인했습니다 — 작업 트리에서 도는 것은 아무것도 증명하지 않기 때문입니다.

부수적으로 알게 된 것 둘, **둘 다 고쳤습니다**:

- **1단계(dry run)가 잘못 통과했습니다.** `Fail the job` 단계에 `dry_run != true`
  조건이 걸려 있어 아무것도 수집하지 못한 드라이런이 초록으로 끝났습니다.
  → **잡을 실패시키지는 않되**(조용한 주말도 같은 모양이라) `::warning::`과 잡 요약에
  이유를 남깁니다. 이유에 `SKIPPED`·`FAILED`가 섞여 있으면 **`::error::`로 올립니다** —
  그건 조용한 날이 아니라 설정이 덜 된 것입니다. (H3)
- **키가 없을 때 `SKIPPED`가 아니라 `FAILED`로 기록됐습니다.**
  → `OpenAlexUnavailable`과 `LLMUnavailable`을 `StageSkipped` 하위로 옮겼습니다.
  **판정은 그대로입니다** — 필수 소스가 빠진 날은 여전히 `not_published`이고,
  **정확해진 것은 이유뿐입니다.** (H2)

### 지금 박사님이 하실 일 — 한 줄

**§4의 0단계로 `OPENALEX_KEY`와 `GOOGLE_API_KEY`를 등록하신 뒤,
이 수정이 푸시된 다음에 2단계를 다시 실행하십시오.** 둘 다 필요합니다 —
키만 넣으면 `classify`가 여전히 실패하고, 수정만 있으면 `collect.openalex`가
여전히 건너뛰어집니다.

## 7. 사람이 필요한 일

| # | 일 | 주기 | 시간 | 명령 |
|---|---|---|---|---|
| 1 | 저널 화이트리스트 검토 | 재생성될 때 | ~20분 | `vocab/sources/journals.yaml` 편집 |
| 2 | 어휘 후보 큐레이션 | 가끔 | ~30분 | `vocab/methods.yaml` · `data.yaml` 편집 |
| 3 | 라벨링 (Q1) | 랭킹을 바꿀 때 | ~15분/일 | `uc review --label relevance --date …` |
| 4 | `unmatched.jsonl` 어휘로 흡수 | 주간 | ~10분 | `runs/*/unmatched.jsonl` |
| 5 | 조용한 날 임계값 재보정 | 백필 후 | ~2분 | `uc calibrate --apply` |

**1·2·4번은 건너뛰면 서서히 나빠집니다** — 화이트리스트가 학습셋을 만들고,
어휘가 모든 오버레이 태그를 만듭니다. **그래도 하루 이틀이 아니라 몇 주 단위로 나빠집니다.**

> **매일 검수(구 Q4)는 재정의 중입니다.** 원래 설계는 매일 15분 검수를 발행의
> 전제로 뒀는데, 자리를 오래 비우는 운영 방식과 맞지 않습니다.
> **발행은 자동으로 하고, 검수는 표본으로 사후에** 하는 쪽으로 바꾸는 작업이
> 진행 중입니다. 그때까지 매일 검수는 **의무가 아닙니다.**

## 9. 절대 하면 안 되는 것

- **`content/` 아래를 손으로 편집** — 파이프라인 산출물입니다. `uc review`를 쓰십시오
- **`.env` 커밋**, 로그·보고서·메트릭에 키 값 출력
- **실제 API를 부르는 테스트**
- **OpenAlex 유래 필드 이름 변경** (`referenced_works` · `topics` ·
  `primary_location` · `cited_by_count`) — Phase 1이 그 이름에 의존합니다
- **이미 배정된 `work_key` 변경**
- **`git push --force`**
- **이미 발행된 이슈를 다시 쓰기** — 발행된 이슈는 불변입니다
